# Shared SED key: provisioning and retrieval

The chosen policy is one shared SED master key for all field controllers and the
compatible home retrieval controller. `examples/shared-key-policy.json` contains
only the reference `rotation-system-v1` and version `v1`; it contains no secret.
Create the actual key ONCE, escrow it, and securely provision the same bytes to
all hosts. Running key-generate independently on two hosts with the same name
creates different keys. Labels and key identifiers do not prove key equality.

No production key was generated, no controller configured and no disk modified
while implementing these workflows. Hardware execution still needs the site
verifier described in commissioning.md. New CLI commands print plans only.
The concrete Linux read-only verification helper is available to that verifier;
it does not replace the missing controller/BMC integration.

## Controller commissioning (one time)

Use a compatible dedicated home controller, with no unrelated data attached.
On each new, unconfigured controller, generate a commissioning plan:

```sh
python3 -m canister plan-commission \
  --target examples/target.synthetic.json \
  --policy examples/shared-key-policy.json
```

Use real target serials before execution. The plan uses the shared SecretRef and
requires controller SED state to be unconfigured, controller maintenance, escrow
and a verified recovery path. Do NOT run MODE enable on every insertion, disable
SED management, or silently change an existing controller key. An already
configured controller needs verification against its commissioning record and a
recovery test. In particular, do not rekey a controller merely to read an export.

## New canister provisioning

```sh
python3 -m canister plan-provision \
  --target examples/target.synthetic.json \
  --policy examples/shared-key-policy.json \
  --size-mib 30000000 \
  --member /dev/disk/by-id/wwn-INCOMING \
  --uuid 11111111:22222222:33333333:44444444 \
  --md-device /dev/md0 --mode extend
```

The example identities, capacity and UUID are placeholders. Stages:

1. Verify four empty factory-state SEDs and claim their security ownership under
   the already configured shared key. Previously used/foreign drives are denied;
   there is no implicit reset fallback.
2. Create encrypted RAID6 using METHOD BUILD and the fixed commissioned size.
   Verify encryption on all four drives, LD identity, and completed initialization.
3. Add the new LD and grow the existing healthy two-copy mirror to three copies.
   Wait for full synchronization before declaring completion.

Use `--mode add` only for a two-member mirror with exactly one missing member.
It replaces that missing member instead of creating three copies. Before the
final stage, bind the new LD's actual WWN/by-id to these exact four drive serials;
a preselected by-id argument must never be assumed correct. If the WWN is unknown
until creation, run the first stages through the integration, discover/verify it,
then deliberately generate the mirror plan. Do not auto-select the first new disk.

`Executor.execute_workflow(workflow, confirmation=target.serial, keys=provider)`
holds one lock across all stages. Each stage's verify_result must wait for its
asynchronous tasks and verify postconditions before the next begins. Failures
stop the workflow without retries or destructive rollback.

## Export manifest

Record actual export ID, four drive serials, MD UUID, filesystem type/UUID, shared
key version, and the consistency boundary in a protected manifest. See
`examples/export-manifest.synthetic.json` for its structure. Protect the manifest
against edits; it is an identity record, not proof by itself. The site verifier
must cross-check actual metadata and the durable export log, including events,
MD member role, sector geometry, LD WWN and completed quiesce/detach. A manifest
is not automatically generated by the generic eject hooks.

The current retrieval workflow supports metadata 1.2 RAID1 with ext4 or XFS
DIRECTLY on the MD device. It refuses LVM, LUKS, nested partitions and other
filesystems. A corresponding explicit reader is needed if that layout changes.

## Home retrieval

Prepare the host BEFORE attaching the canister: prevent MD autoassembly, LVM
activation, automount, and filesystem repair services. Isolate it from the live
production array and any other exports with the same MD/filesystem UUID. Use the
complete four-drive set and a controller/firmware combination whose RAID/SED
import has been tested. Controller initialization, consistency repair and other
background writes must be disabled or prevented according to vendor procedures.
Host read-only settings do not block controller firmware metadata writes.

```sh
python3 -m canister plan-retrieve \
  --target examples/target.synthetic.json \
  --policy examples/shared-key-policy.json \
  --manifest examples/export-manifest.synthetic.json \
  --member /dev/disk/by-id/wwn-EXPORTED-LD \
  --md-device /dev/md127 --mountpoint /mnt/canister-export
```

The target file must identify the HOME controller and the exported drive serials,
not the old field controller. With a matching shared key, first verify whether
the existing encrypted volume is already unlocked. By default the workflow issues
NO ARCCONF mutation. If hardware explicitly reports foreign SED ownership that
requires import, `--foreign-import` adds an import using the shared key. That
stage changes security metadata and is not a forensic read-only operation. It
requires evidence of the foreign state, correct key, no interrupted rekey and
acknowledgment of security-metadata changes; it never creates or resets an array.
If the key does not match, stop and select the archived key version. Do not try
factory-revert or disable SED management.

The host-access sequence is equivalent to the following commands, after all
identity, isolation, consistency and unused-device checks have passed. Replace
the placeholders; these are not commands to copy blindly onto a production host:

```sh
# The member is the existing RAID6 LOGICAL disk, not one of the four raw SSDs.
blockdev --setro /dev/disk/by-id/wwn-EXPORTED-LD
blockdev --getro /dev/disk/by-id/wwn-EXPORTED-LD
# Require output 1 before proceeding.
mdadm --examine --export /dev/disk/by-id/wwn-EXPORTED-LD
# Verify the manifest UUID, metadata 1.2, RAID1, member role/events and no reshape.
mdadm --assemble /dev/md127 --readonly --run --config=/dev/null \
  --uuid=11111111:22222222:33333333:44444444 \
  /dev/disk/by-id/wwn-EXPORTED-LD
blockdev --getro /dev/md127
# Require 1; independently verify MD readonly state, idle sync, UUID and sole member.
# Verify filesystem type and UUID using read-only probing before mounting.
mount -t ext4 -o ro,noload,nodev,nosuid,noexec /dev/md127 /mnt/canister-export
# For XFS instead:
# mount -t xfs -o ro,norecovery,nodev,nosuid,noexec /dev/md127 /mnt/canister-export
```

`--config=/dev/null` avoids importing host mdadm array definitions for this command;
it does NOT disable system-wide autoassembly. That is a separate prerequisite.
`--run` permits starting a degraded array with the supplied member; it does not
request a rebuild. No spare or production peer is supplied. Expected degraded
status on the reader is acceptable. `read-auto` is NOT the same as explicitly
`readonly` and is refused by the verification helper.

Call `verify_readonly_md(member, md_device, expected_uuid)` immediately before
mounting. It checks real block-device identities, both kernel read-only flags,
MD UUID/level/metadata, explicit readonly state, idle synchronization, and exactly
one member matching the export. The site verifier must additionally check the
filesystem UUID/type, mountpoint and absence of unexpected layers. Verify the
resulting mount is ro with the requested no-replay options before handing it to
review software. Applications needing temporary files or database recovery must
use a separate writable copy, never the export.

### If assembly or mounting refuses

STOP. The field detach uses `--fail`/`--remove`, so its recorded member state can
prevent ordinary degraded assembly. This has not been validated on your hardware
or MD version. The script intentionally has no --force path. Never use --create,
--assume-clean, --zero-superblock, writable assembly, fsck repair or automatic
journal replay on the only export to make it mount.

Make a verified block clone of the unlocked RAID6 logical disk onto separate
storage. At this capacity that may itself take hours. Perform any necessary MD
metadata repair, forced assembly or filesystem journal recovery ONLY on the
working clone, using a separately reviewed recovery procedure. Skipping journal
replay can expose an inconsistent filesystem if the export boundary was not
adequate. It does not repair consistency or guarantee an application can open
its database. Establish a reliable export/read cycle in the lab before using
this as an operational grab-and-go process. If direct assembly consistently
fails, revise the field export design; do not normalize forced recovery as the
routine reader path.

### Finish reviewing

```sh
python3 -m canister plan-close-retrieval \
  --target examples/target.synthetic.json --md-device /dev/md127 \
  --mountpoint /mnt/canister-export
```

The plan unmounts and stops only the identified retrieval array. It never changes
the source back to writable. Verify MD absence and no users before the vendor's
safe canister removal procedure. Reboot/hotplug can reset Linux block read-only
state, so protection is re-established for every retrieval session.
